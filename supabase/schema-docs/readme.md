# `README.md` — `/supabase/schema-docs/` Index

This folder is a **current-state reference** for the Maguje FC Supabase project — tables, relationships, views, constraints, RLS policies, storage, auth/roles, and Edge Functions, as they actually exist in the live database.

**This is not the same thing as `/supabase/migrations/`.** The migrations folder is a historical change log — useful for seeing how the schema evolved over time. This folder is a snapshot of *current state*, generated by querying the live database directly rather than reading through migration files, since not every change applied to the live project is guaranteed to have a corresponding local migration file.

## Files in this folder

| File | Contents |
|---|---|
| `tables.md` | Every table: columns, types, nullability, defaults |
| `relationships.md` | Every foreign key, grouped by domain, plus notable non-relationships worth knowing about |
| `views.md` | Every view's full SQL definition, grouped by purpose (standings, head-to-head, player stats/spotlight, search) |
| `constraints.md` | Every CHECK constraint, by table, with the rule it enforces |
| `rls-policies.md` | Every Row Level Security policy, by table, plus the key access-control mechanisms used throughout (`my_role()`, owner-email gating, content-manager delegation windows) |
| `storage.md` | Storage buckets and folder-level access policies |
| `auth-and-roles.md` | The admin/role model — identity, login flow, the 4 roles, the owner-only tier, delegated access |
| `edge-functions.md` | Every deployed Edge Function, what it does, and its security posture |

## How to keep this current

**Regenerate the relevant file after any schema change** — this documents current state, not history. A file left stale after a migration is worse than no documentation at all, since it'll be trusted and wrong.

If you don't have a way to regenerate it yourself, ask Claude (or whoever's assisting) to re-run the same live-introspection queries used to build it originally — direct SQL against `information_schema`, `pg_policies`, `pg_constraint`, `pg_get_viewdef()`, and the Supabase Storage/Edge Functions APIs, not a read of the migrations folder.

## Known issues surfaced while building this reference (as of this writing)

These are documented as findings, not yet fixed — decide and address separately:

1. **`invite-manager` Edge Function writes to a table called `system_logs` (plural)** — the actual table is `system_log` (singular). This insert silently fails every time; manager invites still succeed, but no audit log entry is ever created for them. See `edge-functions.md`.
2. **Stale references to the removed Activities feature:** `post_media_post_type_check` still allows `'activity'` as a valid value, and three storage policies still reference an `activities/` folder. See `constraints.md` and `storage.md`.
3. **`players` table write access is granted to both `senior_manager` and `match_manager`** — confirm this overlap is intentional. See `rls-policies.md`.
4. **`login_sessions` has no visible INSERT policy for any admin role** — worth confirming how session logging currently succeeds (likely a service-role or trigger path not covered by client-facing RLS). See `rls-policies.md`.
5. **Two overlapping storage policies both grant `match_manager` write access to `players/`** — harmless, but worth consolidating if this area is ever refactored. See `storage.md`.
